# Security Policy

## Scope

This policy applies to the open-u60-pro toolkit code (zte-agent including its web UI, iOS app, Android app). It does **not** cover ZTE firmware or hardware vulnerabilities — please report those directly to ZTE.

## Reporting a Vulnerability

If you discover a security vulnerability in this project, please report it responsibly:

1. **Do not** open a public GitHub issue.
2. Email **jesthersilvestre@yahoo.com** with:
   - A description of the vulnerability
   - Steps to reproduce
   - Potential impact
3. You will receive an acknowledgement within 72 hours.
4. A fix will be developed privately and disclosed once a patch is available.

## Supported Versions

Only the latest release on the `main` branch is actively supported with security updates.

## Security Considerations

- `zte-agent` listens on `0.0.0.0:9090` (`ZTE_AGENT_BIND` changes it) over plain HTTP. It is meant for the router's own network and, if you enable Tailscale, your tailnet. The password, tokens and session cookie can be read by anyone who can watch traffic on the network: use a strong Wi-Fi password, use the web UI's HTTPS on the LAN (below), and use Tailscale (encrypted) for remote access.
- **LAN HTTPS with the router's own certificate authority** (off until the owner turns it on in Settings › HTTPS & Install as App):
  - The agent creates a root certificate authority and one issuing CA (ECDSA P-256), both with critical **name constraints**: they may only vouch for this router, its LAN address at the time HTTPS is turned on (e.g. `192.168.0.1`, if it is a private address) and the name `u60.home.arpa` (under `home.arpa`, a zone reserved for home networks); every IPv6 address is excluded, and every IPv4 address when the LAN address is not private; both are limited to TLS server certificates (extended key usage serverAuth). The root's private key is dropped (and wiped from memory) as soon as it has signed the issuing CA and is never stored. The issuing CA signs the server certificate for the router's LAN address and `u60.home.arpa` (at most 397 days). After a LAN address change only `u60.home.arpa` works until HTTPS is reset (a new CA for the new address).
  - Why two: some verifiers ignore name constraints in a root the user installed (Android's system verifier, which Chrome for Android uses, accepted a certificate for `example.com` under such a root in our test), but every verifier enforces them in an intermediate. Tested: a certificate for a name or address outside the constraints, signed by the issuing CA, is refused by Chrome for Android 133 (Android 16), Safari on iOS 26.5, macOS's trust evaluation, OpenSSL 4 and rustls/webpki.
  - Trusting the root means: any certificate it vouches for is believed for TLS on that device, so someone who stole the issuing CA's key from the router (`/data/zte-agent-tls/issuing.key`, mode 0600, readable by root on the router) could impersonate `https://<that LAN address>` and `u60.home.arpa` to devices that trust it, on any network (for example another router whose admin page is also at 192.168.0.1), but no other address or name: the constraints, not the CA's `pathLen`, are what hold (a CA that key makes for itself still inherits them). Nothing can revoke the key; Reset HTTPS and removing the CA from each device are the way out. Whoever has root on the router can already change everything the web UI shows. Keys are never logged, rendered or served; only the root's certificate (public) is offered for download.
  - **Trust is set up over plain http.** A device that does not trust the CA yet downloads it, and reads its fingerprint, from `http://…:9090`. Someone on your Wi-Fi who can intercept traffic (they know the Wi-Fi password and spoof ARP) could replace both with their own unrestricted root and a matching fingerprint; a device that trusts that root can then be intercepted on every website. So check the fingerprint against a source that does not come over that channel: the same page opened over HTTPS on a device that already trusts the router's CA, or `sha256sum /data/zte-agent-tls/ca.crt` over SSH (the agent also logs it at Turn On). The USB cable does not help (USB networking is bridged into the same LAN). This risk comes with decision 59 itself.
  - Plain http on port 9090 keeps working (the apps use it). There is no HSTS: it would also force https onto port 9090 of the same address.
  - **Reset HTTPS** (Settings) deletes the certificate authority, the certificates and the local name, closes the port and ends every open HTTPS connection (a request in progress may finish within 2 seconds). Remove the old certificate authority from every device that trusted it; turning HTTPS on again makes a new one, which each device must trust again.
- **The agent refuses connections from the mobile-data side itself**, whatever the router's firewall says (the web UI can turn the firewall off or set it to Low). It serves a connection only when the client's address is loopback (every Tailscale client: tailscaled runs with userspace networking), one of the router's own addresses, an IPv6 link-local address that came in on a local interface, or inside the subnet of a local interface: the Wi-Fi bridge `br-lan`, the USB network, any interface not named `rmnet*` (the cellular data interfaces). The most specific subnet holding the address decides, as the kernel's replies follow it: a LAN subnet that also covers the cellular interface's (a 10.0.0.0/8 LAN and a carrier address in 10/8) does not let the carrier's side in, and a tie is refused. Any other connection is closed without a reply and logged (the first, then at most one line a minute; the address, never what was sent). The client's address is what counts, so a port forward or DMZ that sends internet traffic to the router's LAN address is refused too.
  - The interface table comes from `getifaddrs`, read off the HTTP thread, at a connection that needs it (never for Tailscale): when it is 5 s old, or when a connection would be refused (at most once a second for those). New connections wait at most 0.5 s for a read; a slower one (the kernel's lock held while Wi-Fi is reconfigured) finishes in the background while the last table decides. A failed read keeps the last table for 10 minutes; with none that recent the agent serves every connection (fail open, logged once; the firewall questions then say this web UI may become reachable): the router's firewall is then the only guard, and a lookup error never locks you out over Wi-Fi, USB or Tailscale.
  - `ZTE_AGENT_ALLOW_MOBILE=1` turns the check off (logged at startup; any other value is ignored, which is logged too); the firewall questions then say again that this web UI may become reachable from the mobile network.
  - With `ZTE_AGENT_BIND=[::]:9090`, a LAN client using a global IPv6 address that is not in a prefix of a local interface (some carriers share their /64 with the LAN that way) is refused; IPv4 and link-local work.
  - Turning the firewall off or lowering its level can still make the router's other services (SSH on port 2222, the firmware's own web pages) reachable from the mobile network; the web UI says so before it does it. Never forward port 9090 to the internet.
- **Set an agent password** (`ZTE_AGENT_PASSWORD`; `setup.sh` and the browser installer always set one; an empty value counts as none). With a password:
  - every `/api` route except `POST /api/auth/login` needs a bearer token. Tokens are 32 random bytes from the OS. They expire after 1 h without use and at most 24 h after login, on the boot clock, so network time changes do not affect them. At most 32 are kept.
  - the web UI (`/ui/`) uses a session cookie with `HttpOnly; SameSite=Strict; Path=/ui/`, valid 12 h without use and at most 7 days. Sessions are held in RAM, so an agent restart logs browsers out. Over HTTPS every web UI cookie is a `__Host-` cookie (`__Host-zte_ui_session`, `…_pre`, `…_theme`, `…_refresh`; `Secure; Path=/`): cookies are per host, not per port, and this way the http and https pages of one address can neither read nor overwrite each other's; the https side ignores the http side's cookies, which browsers also send to it.
  - every web UI form carries a per-session CSRF token and must come from the same origin (`Origin`, or `Referer` if there is no `Origin`; a foreign `Sec-Fetch-Site` is refused). Changes that can cut the connection or are destructive (mobile data off, roaming on, airplane mode on, a network mode, band and cell locks, WiFi, APN, LAN, DNS and firewall changes, deletes) need a separate confirmation page, and the forms that change the router carry a single-use token, so a double submit sends once.
  - Reboot Router and Factory Reset (and Mobile Network's "Reboot Now") also need the agent password, checked on the router in constant time and counted by the login rate limit; it is never echoed or logged.
  - Wi-Fi, guest Wi-Fi and APN passwords and SMS forwarding secrets are never put into a page (the field is empty: leave it empty to keep the current one); a password typed into a form that was refused, or whose change failed on the router, waits in RAM for that session only so the next try from that form sends it; it is dropped once sent, on logout, or an hour after the last try. The Wi-Fi password appears only on the no-store "Share Wi-Fi" page.
  - Two preference cookies, `zte_ui_theme` and `zte_ui_refresh` (`HttpOnly; SameSite=Strict; Path=/ui/`), take only fixed values (System / Light / Dark; 1.0–10.0 s in 0.5 s steps).
  - logins are rate limited: per client address (5 failures, then 1 s doubling up to 5 min) and globally (30 failures, one more allowed every 10 s), answered with `429` and `Retry-After`. Existing tokens and sessions keep working. All Tailscale clients share one address, whose blocks stop at 10 s.
- Against DNS rebinding the agent answers only requests addressed to an IP address, a name in `ZTE_AGENT_UI_HOSTS`, the LAN HTTPS name (`u60.home.arpa`, `ZTE_AGENT_TLS_NAME`) over HTTPS only (another network's DNS can answer for that name, but only the router has its certificate), or, from Tailscale clients, `localhost` and the router's Tailscale names. This applies to every request without a password, and with one to the web UI and to every browser request (`Origin` or `Sec-Fetch-Site`) to the API, the login included.
- Without a password the JSON API is open to every device on the network (within the host rule above). The web UI, `/api/events` and the Live Activity routes are refused.
- State-changing browser requests from another site are refused (403) whether or not a password is set. The web UI sends a Content-Security-Policy that allows only scripts carrying a per-response nonce (Datastar on live pages, and under the System theme the small `theme.js` that recolours iPhone's status bar after a light/dark switch), `X-Frame-Options: DENY`, `Cross-Origin-Resource-Policy: same-origin` and `Cache-Control: no-store` on pages.
- Cookies are not port-scoped: the stock ZTE web UI on port 80 of the same address shares the agent's cookie jar, and ZTE's HTTPS server on port 443 of the same host could also set or overwrite the agent's `__Host-` cookies (the Origin and CSRF checks still refuse its requests: at most it logs a browser out). To keep them apart, open the agent under its own host name (listed in `ZTE_AGENT_UI_HOSTS`), or over HTTPS at `https://u60.home.arpa:9443/`, which ZTE's servers do not answer to by that name.
- Besides the `SameSite=Strict` session cookie, login sets a marker cookie (`zte_ui_signed_in=1`, `SameSite=Lax`, no secret) so that Chrome for Android's installed app, which arrives without the strict cookie, can open the same page once more as a same-site navigation and find the session. That second request is a GET of the request's own page only; posts still need the strict session cookie, the CSRF token and the Origin check.
- To revoke every token and session (a lost phone, a leaked password), set a new agent password (`./deploy.sh <new-password>`); the restart ends all of them.
- The agent never logs passwords or tokens.
- SSH credentials and device access tokens should never be committed to the repository.
