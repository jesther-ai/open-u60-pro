# Web UI: `/ui/`

The agent serves a browser UI on the same listener as the JSON API (port 9090) and, once the owner turns it on, over HTTPS on port 9443 with the router's own certificate authority ([LAN HTTPS](#lan-https)). It is a copy of the iOS app, tab by tab (Dashboard, SMS, Tools, Router, Settings), with the same screens, words and flows: the dashboard with its USB-C card and its sheets (Connection & signal, Live traffic, Battery Details, CPU & temperatures, CPU & Memory, Processes, Wi-Fi & devices with Share Wi-Fi), Network Mode, the Tools list with Automations (New / Edit Automation), Speed Test, Enable ADB, USB Mode, Band Lock, AT Terminal, Device Info, Connected Devices, the app's placeholders for its shell tools and notes for the two tools that stay in the app (LAN Speed Test, Config Decrypt/Encrypt), Router › Mobile Network (mobile data, airplane mode, connection mode, data roaming, network selection with its scan and manual registration, and the app's "Reboot Required"), Cell Lock (with the neighbour scan), Smart Tower Connect, Signal Detection, SIM Card (with its PIN, PUK and unlock-code sheets), eSIM Profiles (switch, rename, delete, operator receipts, the chip card, and Add eSIM from a photo of the QR code or the code), SIM Services (USSD and the SIM Toolkit), WiFi, Guest WiFi, APN (with New / Edit APN and Auto APN), LAN / DHCP, DNS (with the DoH cache inspector), Firewall (with New Port Forward), Telemetry Blocker, VPN Passthrough, QoS and Device Controls (charge limit, Power-save Mode, Fast Boot, Auto Sleep with its idle timeout, Reboot Router and Factory Reset with the router password), SMS › Messages with its conversations (open, reply, delete) and New Message, SMS Forwarding (its switches, rules, New Rule / Edit Rule with Test Destination, Forward Log with Retry and Clear; also under Tools), and Settings (Session with Log out, the Polling refresh interval, the Appearance theme, HTTPS & Install as App with Install on Your Devices, About, Legal). What the web leaves out is listed under [Not on the web](#not-on-the-web). For users, see the README's [Web UI](../README.md#web-ui) section; this page is for contributors.

- Server-rendered HTML ([maud](https://maud.lambda.xyz/)): every interpolated value is escaped, and nothing under `src/web` uses raw HTML (a test checks this).
- Pages call the agent's own handler and service functions in-process, never the agent over HTTP.
- Everything works without JavaScript. [Datastar](https://data-star.dev/) 1.0.4, vendored and served by the agent, is an optional live layer.
- Sessions live in RAM only: an agent restart logs every browser out.
- Screens and actions are tables (`src/web/screen.rs`, `action.rs`, the tabs in `src/web/tabs/`), drawn with shared primitives (`kit.rs`); one route table (`routes.rs`) serves them all.

## Navigation

- Every signed-in page has a nav bar (title in the middle; on the left "‹ <parent>", the dashboard's status pill, or Connection & signal's age badge; on the right "Done" or the dashboard's age badge; both sides keep the same width, at least 4.5rem, so the title stays centred and a long way back or title ends in "…") and the five-tab bar: a floating bar at the bottom on phones, under the nav bar on wide screens. Both are plain links; no JavaScript is involved.
- App sheets are pages with "Done" on the right (Connection & signal, Live traffic, Battery Details, CPU & temperatures, Wi-Fi & devices); Processes, a sheet over CPU & Memory, has "Done" on the left and "Kill All Bloat" on the right, as the app's. Pushed screens have "‹ <parent>" (Router › Mobile Network, every Tools screen; CPU & Memory, a sheet over CPU & temperatures; Share Wi-Fi, a card the app expands in its sheet). Alerts are confirmation pages: "‹ <form's screen>" and "Confirm" in the nav bar, the question as the page's heading (it wraps), what happens, the button and Cancel.
- The app's USB Mode sheet, which it opens by itself over any tab when a USB-C cable is attached, is a card on the dashboard after the banners (a page cannot pop up a sheet, and nothing is sampled for the other pages).
- One screen can sit in two tabs: Network Mode is pushed from Connection & signal (`/ui/signal/network-mode`, Dashboard tab) and listed under Router (`/ui/router/network-mode`); SMS Forwarding is pushed from Messages' gear (`/ui/sms/forward`, "‹ Messages") and listed under Tools › Automation (`/ui/tools/sms-forward`, "‹ Tools"). Each mount has its own tab, way back and form targets.
- Messages leads with the gear (SMS Forwarding) and trails with New Message, as the app; the app's Call button is left out (calls are app-only; the page says so). A conversation is pushed from Messages ("‹ Messages", keeping the storage filter). New Message (the app's sheet) has "Cancel" on the left. The app's swipe to delete is a small "Delete" link at the end of each row, which opens a confirmation page. During a search, "Cancel" beside "Search" leads back to the whole list (the app's search bar).
- New Rule / Edit Rule (the app's sheet) has "Cancel" on the left, back to SMS Forwarding; each rule row of SMS Forwarding has its switch and a "Delete" link (the app's swipe), which asks first.
- Forward Log is pushed from SMS Forwarding ("‹ SMS Forwarding", in the mount's tab) with "Clear" on the right (the app's toolbar button), which asks first; a failed entry's "Retry" (the app's swipe) is a small button at the end of its row.
- Tools lists the app's rows in its sections and order (`ToolsListView`), each with the Android app's subtitle (the iOS rows have none); every row opens its screen or its note. TTL Settings, Enable SSH and Device Explorer open the app's placeholders (its icon, title and text); LAN Speed Test and Config Decrypt/Encrypt open a note in the same style: "LAN Speed Test is in the OpenU60 app." (it measures in the client, which needs a script) and "Config Decrypt/Encrypt is in the OpenU60 app." (the app's title "Config Tool"; it decrypts a credential-bearing config file on the phone). Processes stays under the dashboard (the app's place; Android also lists it under Tools).
- New Automation / Edit Automation (the app's sheet) has "Cancel" on the left, back to Automations; each automation row has its switch and a "Delete" link (the app's swipe), which asks first.
- Speed Test, Enable ADB, Band Lock and AT Terminal are pushed from Tools ("‹ Tools"); their questions (the web's, and the AT Terminal's "Dangerous Command", the app's alert) are confirmation pages that lead back to the tool.
- Router's screens are pushed from Router ("‹ Router"): Mobile Network, Network Mode, Cell Lock, Smart Tower Connect, Signal Detection, SIM Card, eSIM Profiles, SIM Services, WiFi Settings, Guest WiFi, APN Settings, LAN / DHCP, DNS Settings, Firewall, Telemetry Blocker, VPN Passthrough, QoS, Device Controls. Device Controls' password sheets, Reboot Router and Factory Reset, are pages with "Cancel" on the left; their answer is the "Rebooting…" (or "Resetting…") page, which has no way back but the tab bar and "Reload". Auto Sleep on is asked first on a confirmation page ("‹ Device Controls") for a remote browser only. Firewall's sheet New Port Forward is a page ("Cancel" on the left); the app's swipe to delete a port forward or a blocked domain is a trash button at the end of its row, which asks first. The questions of Firewall (each switch, the level, Apply DMZ, Add Rule, a rule's delete) and a blocked domain's removal are confirmation pages ("‹ Firewall", "‹ Telemetry Blocker"). APN Settings' sheets are pages: New APN and Edit APN ("Cancel" on the left; a manual profile's row opens Edit APN, its "•••" menu has the app's swipes, Activate and Delete) and Auto APN ("Done"). DNS Settings' "Inspect Cache" opens DNS Cache ("Done"). The questions of WiFi, Guest WiFi, APN (mode, Add / Save, Activate, Delete), LAN / DHCP and DNS (Apply, Clear Cache) are confirmation pages ("‹ <screen>"; Cancel leads back to the form as typed); after WiFi's Apply comes "Reconnect to …", after LAN's the page with the new address. SIM Card's sheets (Enter PIN, Enable PIN Lock, Disable PIN Lock, Change PIN, Enter PUK, SIM Unlock) are pages with "Cancel" on the left, back to SIM Card; each is also its own question (below). "Reboot Required" (the app's alert after airplane mode off failed twice) is pushed from Mobile Network ("‹ Mobile Network"). The questions of Apply (roaming), a registration, the cell locks and unlock and the STC controls are confirmation pages that lead back to their screen; a scan, a registration and a changed connection mode or roaming continue on an operation page.
- eSIM Profiles has the app's toolbar on the right: "+" (Add eSIM) and Refresh. Its dialogs are pages pushed from it ("‹ eSIM Profiles"): Switch to …? and Delete … permanently? (confirmation pages), and Rename profile (the app's sheet, "Cancel" on the left). The app's swipes and context menu are a "•••" menu on each profile (a `<details>`: Rename, Delete profile); tapping a profile that can be switched to opens its question, as the app's tap. A switch continues on an operation page ("‹ eSIM Profiles"). Add eSIM ("+", the list's Add eSIM, the app's sheet) has "Done" on the right ("Close" while a download runs; live, so it reads "Done" once the download ends), back to eSIM Profiles; its download card is the sheet's progress view, and "Switch to it now" leads to the eSIM Profiles switch question.
- Settings is a tab root in the app's order: "Session" ("Signed in in this browser", "Log out"; it takes the place of the app's Gateway and Keychain sections, which have no web counterpart), "Polling", "Appearance", "About", "Legal". The Polling and Appearance footers are the app's plus "Saved in this browser." (they are this browser's cookies). A web addition sits after Appearance: "HTTPS & Install as App" ([LAN HTTPS](#lan-https)); its "Install on Your Devices" is pushed ("‹ Settings"), its Turn On, Renew and Reset questions are confirmation pages ("‹ Settings").
- The login page is the app's header ("ZTE U60 Pro", "Router Companion"; no "U60 Pro" brand over it, as the app's login has no title) with the web's "Agent password" and "Log in"; other signed-out pages keep the brand.

## Request pipeline

Before any request, the listener checks the connection (`httpd::mobile`, owner decision 53; the API too): a client on the mobile-data side is closed without a reply, whatever the router's firewall says. Served: loopback (every Tailscale client), the router's own addresses, an IPv6 link-local address that came in on a local interface, and addresses in the subnet of an interface not named `rmnet*` (Wi-Fi's `br-lan`, the USB network) when that is the most specific subnet holding them (the kernel replies through it; a tie with an `rmnet*` subnet refuses). The client's address counts, not the one it reached, so a port forward or DMZ to the router's LAN address is refused too. The table is `getifaddrs`, read on the blocking pool (the accept loop awaits it for at most 0.5 s, then decides with the last table while the read finishes in the background, starting no other; open connections keep being served) at an accept that needs it (not loopback): when 5 s old, or when a connection would be refused (at most once a second for those). A failed read keeps the last table for 10 minutes; with none that recent everything is served (logged once; `mobile::mobile_served` then switches the firewall questions to their old wording); `ZTE_AGENT_ALLOW_MOBILE=1` turns the check off (another value is ignored and logged). Refusals are logged once, then at most one line a minute; a client in no local subnet (a port forward's or DMZ's) is logged as "no local subnet, reached via <interface>".

One middleware (`guard` in `src/web/mod.rs`) runs first on every `/`, `/ui` and `/ui/**` request:

1. **Host allowlist** (DNS-rebinding defence): an IP literal, a name in `ZTE_AGENT_UI_HOSTS`, the LAN HTTPS name (`u60.home.arpa`) only over the HTTPS listener (which runs only while HTTPS is on: another network's DNS can answer for a `home.arpa` name too, so over http it would be a rebinding target, but no one else can present the router's certificate for it), and, only from loopback peers (Tailscale clients), `localhost` and the router's Tailscale names. Otherwise `403 Host not allowed`; no `Host` is `400 Missing Host`. The API applies the same rule.
2. A fresh CSP nonce for every HTML response.
3. Without an agent password, every page is the "Set an agent password" page (`403`); assets and the manifest still load.
4. Security headers on every response:
   - `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`;
   - HTML: `Content-Security-Policy: default-src 'none'; script-src 'nonce-…'; style-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'; manifest-src 'self'` and `Cross-Origin-Opener-Policy: same-origin`;
   - HTML and live streams: `Cache-Control: no-store`.
5. A browser whose theme is Light or Dark (Settings › Appearance, the `zte_ui_theme` cookie: `light` or `dark`, anything else is the system's) gets every HTML page, signed in or not, in that scheme (`prefs::themed`): the shell's colour-scheme tags, drawn for the system's scheme (`color-scheme: light dark` and a nav bar colour per scheme), are swapped for the theme's (`color-scheme` and one nav bar colour) plus `theme-light.css` or `theme-dark.css` after `app.css`. No JavaScript; a page under the System theme is passed on untouched.

Then the session, CSRF and the gate: page work that reads the device waits for a general-lane permit like an API call; when none is free within 7 s the page is `503` "Router busy" with a Retry link.

## Sessions and CSRF

- Cookie: `zte_ui_session=<64 hex>; Path=/ui/; Max-Age=604800; HttpOnly; SameSite=Strict` (host-only; over plain HTTP on :9090 without `Secure`, over HTTPS on :9443 as `__Host-zte_ui_session; Path=/; …; Secure`). With it the marker `zte_ui_signed_in=1; …; SameSite=Lax` (no secret; the marker hop above). Cleared with `zte_ui_session=; Path=/ui/; Max-Age=0; HttpOnly; SameSite=Strict`.
- A session lasts 12 h without use and at most 7 days. At most 16 are kept; a new login drops the least recently used. Logging in replaces the sessions the browser presented; logging out ends the session and its live streams.
- Cookies are never read under `/api`, and bearer tokens are ignored under `/ui`. A bearer token is never accepted as a cookie, or the reverse.
- Up to 16 well-formed session cookies per request are tried, so cookies another page on the same host planted with deeper paths (cookies are not port-scoped) cannot push the real one out. A dedicated host name in `ZTE_AGENT_UI_HOSTS` keeps the agent's cookies apart from the stock web UI on port 80.
- **Login form:** a `zte_ui_pre` cookie (`Max-Age=900`) plus an HMAC form token valid 15 min (its time field is offset per process, so it does not reveal the router's uptime), and a hidden username field for password managers. Wrong passwords count against the same rate limit as the API (`429` page with `Retry-After`).
- **`next`** (where the login returns to): starts with `/ui/`, at most 200 bytes, a plain character set, no `//` or `\`, no dot segments (also `%2e`), and never the login, logout, live, asset or operation paths. Otherwise the dashboard.
- **Every form** (login, logout, every change) carries a CSRF token: a random 32-byte secret per session, compared in constant time. The post must also be same-origin: `Origin` must match `Host` exactly (scheme, host, port), or, without `Origin`, `Referer`; a `Sec-Fetch-Site` other than `same-origin`/`none` is refused. Any failure is a `403` page and nothing changes.
- A post without a session is never run: the login page says "Your session expired. Nothing was changed." and leads back to the form's page.
- **Over HTTPS** (`httpd::tls`) every cookie above is a `__Host-` cookie with `Path=/` and `Secure` (`__Host-zte_ui_session`, `__Host-zte_ui_pre`, `__Host-zte_ui_theme`, `__Host-zte_ui_refresh`), so the http and https origins of one host (cookies are per host, not per port) never share a session or a preference: the TLS edge hands the app only this origin's `__Host-zte_ui_*` cookies, without the prefix (the http side's, which browsers send along, are dropped), and turns the app's `Set-Cookie` into `__Host-…; Path=/; Secure` (the clearing ones too). An `https://` `Origin` or `Referer` reaches the checks as `http://` with the same host and port, an `http://` one as `null` (foreign), so the same-origin rules compare host and port exactly as on :9090. No HSTS. The http origin cannot set or read a `__Host-` (Secure) cookie; the session store is shared, so a session token is valid on either origin only if its cookie gets there, which the browser does not do. Cookies are not port-scoped, so another HTTPS server on the same host (ZTE's uhttpd on :443 of 192.168.0.1) could set or overwrite `__Host-zte_ui_*` cookies; the Origin and CSRF checks still refuse its requests, so the most it can do is log a browser out (cookie tossing).
- **Preferences** (Settings › Polling and Appearance, `web::prefs`): `zte_ui_theme=light|dark` and `zte_ui_refresh=<ms>`, `Path=/ui/; Max-Age=31536000; HttpOnly; SameSite=Strict`, set by a CSRF-checked POST (no single-use token: a repeat sets the same value; a value the form does not offer is `400`); the default (System, 2.0 s) clears the cookie. They hold fixed values only and belong to the browser, not the session (logging out keeps them). Like the session cookie, the first well-formed value counts, so one planted by another port of the host with a deeper path can only choose among the same values.

## Live updates

- A live page has one `data-init`, which opens the stream once the page is visible. Datastar closes it while the page is hidden and opens a new one when it is shown again. Each page load has its own stream URL, so a reconnect replaces only its own earlier stream.
- The first frame carries every fragment of the page; then only fragments whose HTML changed (at most every 250 ms), plus a heartbeat after 1 s and then every 5 s.
- The heartbeat restarts a CSS animation: after 15 s without one the page shows "No updates for 15 s · Refresh". No script timer is involved.
- The dashboard's status is the nav bar pill: "Snapshot" (a reload link) without JavaScript, with "over 1 min old" / "over 5 min old" appearing by CSS where the age badge would be, "Connected" while heartbeats arrive, "Offline" (a reload link) after 15 s without one. The app's pill shows the sign-in state; on the web, the stream is the closer equivalent. The age badge ("4s ago") moves with every reading and heartbeat and is shown only while live (a snapshot's would never move). On the dashboard it counts from the last good signal reading (the app's moves only when a refresh answered); on Connection & signal from the last read, failed or not (as the app's sheet).
- The dashboard's cards show no age (as the app's); a card whose topic fails to read says "Couldn't update: <error>" (a web addition). The traffic caption ages from the last good sample. The sheets' age line appears once a topic is 3 cadences old.
- Endings, shown in the status line (on the dashboard: "Offline" in the pill, the reason under the nav bar): signed out (with a Log in link), "Opened in another tab" (a session's fourth stream replaces its oldest), router standby, and "Live updates paused after 30 minutes" with Resume.
- **Refresh interval** (Settings › Polling, the app's slider: 1.0–10.0 s by 0.5 s, default 2.0 s): a live page of this browser asks the hub for that signal cadence (`signal_hint`, as `signal_ms` does for the apps; the hub uses it only with `signal`, and the fastest open stream wins); a screen with its own cadence (eSIM Profiles' 10 s) keeps it. It changes nothing while no page is open: a page load reads once, as always. The app's footer stays true: traffic is read every second.
- Live pages share the hub's 8 streams with `GET /api/events`, and each open live page holds one; when they are all taken the page says "Live updates busy (too many open pages)". The more screens become live, the sooner a household of open tabs and the apps reaches that cap.

- **Rolling numbers** (owner decision 57, the app's `AnimatedNumber`: `.contentTransition(.numericText(value:))`, 0.4 s ease-in-out; `web::roll`). On a live page, when a patch changes a number, its changed digits roll in: up (the new digit rises from below, the old one leaves upwards) when the value went up, down when it went down; the other digits, the sign, the decimal point and the unit stay still. Where (the app's animated values and their web places):

  | App (`AnimatedNumber` / `numericText`) | Web (fragment: number) |
  |---|---|
  | Dashboard Connection card RSRP | `card-conn`: NR/LTE RSRP |
  | Cellular card live speeds and totals | `card-traffic` (dashboard and Live traffic): Download, Upload, Total DL, Total UL |
  | Battery card W / mA | `card-battery`: the power after the status |
  | CPU card usage, temperatures | `card-health`: CPU %, CPU and Battery °C; `hl-cpu`, `hl-temps`, `hl-all` (CPU & temperatures, every sensor); `hc-use`, `hc-temp` (CPU & Memory) |
  | Battery Details Voltage, Current, Power | `bat-detail`: the same three rows |
  | Wi-Fi & devices count, Connected Devices count | `card-devices` (dashboard), `wf-count` (Wi-Fi & devices) |
  | Signal monitor metrics (RSRP, RSRQ, SINR, RSSI) and whole-number rows | `sig-nr`, `sig-lte` (each carrier's grid; PCI, Cell ID, Channel/EARFCN), `sig-wcdma` (RSCP, Ec/Io) |
  | Speed Test progress % and live Mbps | `st-run` |
  | `LastUpdatedView` ("4s ago") | the nav bar's `#age` badge (dashboard, Connection & signal), always rolling up as the app's `numericText()` |
  | Device Controls charge limit, resume gap | no web equivalent: the web's selects are a form, not live |

  - Server side only, no script beyond Datastar. A page load (and so every page without JavaScript) and a stream's first frame draw plain text, byte for byte as before: nothing rolls on a first render or a reconnect. Each stream keeps the numbers it drew (`Views::roll`); a number whose text changed is drawn as its whole text once for screen readers (`.sr`) and an `aria-hidden` copy (`.rl`) in which each changed digit is `<i id="<key><place><digit>" data-u|data-d="<old digit>">`. Datastar's morph keeps an element only when its id matches, and the id holds the digit, so a changed digit is always a new element whose CSS animation runs, and an unchanged digit is plain text. Until the number changes again it is drawn the same way, so a number that did not change costs no patch and a fragment re-sent for another reason restarts nothing. Keys are per page (`roll` keys are lowercase letters; a test renders every live screen twice and checks the digit ids are unique).
  - CSS: tabular digits (`.rl` and every element that holds a rolling number), the column clipped to the line (`clip-path`), the old digit as `::before`; `prefers-reduced-motion: reduce` turns the animation and the leaving digit off. The direction compares the values as the app does (`1,024` and a leading minus are understood; a unit change such as 999.9 Kb/s to 1.2 Mb/s rolls down, as in the app).
  - Cost: a number keeps its roll markup until it changes again (that is how morph keeps the ids), so every later patch of its fragment carries it for each number that has changed on that stream: a per-stream, bounded cost, no extra frames. Measured on the fake-reader harness, where every sampled value changes at every sample (more than a router does): the dashboard's stream 1,605 to 2,343 B/s (+738 B/s), Connection & signal 1,549 to 2,532 B/s, CPU & temperatures 763 to 1,001 B/s; per dashboard frame with everything changed, +32 % bytes (2,280 to 3,012) and +6 % render time (release build).
  - Layout: `.rl` is `inline-block`; a rule that sets `display` on every `span` of a container would beat it and break the line (Connection & signal's grids did: `.metrics .lbl`, not `.metrics span`; `web::tests::no_rule_sets_display_on_every_span`).

## LAN HTTPS

Owner decision 59 (superseding 56: no Tailscale): Chrome installs a web app only from a secure origin (`Page.getInstallabilityErrors` on `http://192.168.0.1:9090/ui/login` reports only `not-from-secure-origin`), so the agent can serve the UI over HTTPS on the LAN with its **own certificate authority**. Offline, no accounts; each device trusts the CA once. Plain http on :9090 stays for the apps and as fallback. Code: `src/tls/` (the manager, `x509`, `hosts`), `src/httpd/tls.rs` (the listener), `src/web/pages/https.rs` (Settings).

**Certificates** (`tls::x509`, DER built by hand and signed with ring, which rustls already links, and p256 for the root, which the Live Activity already links: no certificate crate, no new download; `tls::x509::tests` parse every field back):

| | Root (`ca.crt`) | Issuing CA (`issuing.crt`, `issuing.key`) | Server (`server.crt`, `server.key`) |
|---|---|---|---|
| Key | P-256; **dropped** once it has signed the issuing CA (p256's key, wiped when dropped), never on disk | P-256, 0600 | P-256, a new one at every issue, 0600 |
| Subject | `O=OpenU60 zte-agent, CN=U60 Pro local CA <8 hex>` (unique per CA) | `… CN=U60 Pro issuing CA <same hex>` | `CN=u60.home.arpa` |
| Validity | 10 years from 2 days back | the same | 397 days from 2 days back, never past the issuing CA |
| basicConstraints (critical) | CA, pathLen 1 | CA, pathLen 0 | not a CA |
| keyUsage (critical) | keyCertSign, cRLSign | keyCertSign, cRLSign | digitalSignature |
| extKeyUsage | serverAuth | serverAuth | serverAuth |
| nameConstraints (critical) | permitted: IP `<LAN address>/32` (`br-lan`'s IPv4 at Turn On, if private) and DNS `u60.home.arpa`; excluded: IP `::/0`, and `0.0.0.0/0` when no address is permitted | the same | — |
| SAN | — | — | DNS `u60.home.arpa`, IP the LAN address while the CA covers it |

- **Scope (owner decision 59: "the router's private addresses and a local name").** The CA can vouch for exactly what the server certificate needs: the LAN address it was made for and `u60.home.arpa` (with names below it). Someone who copied `issuing.key` from the router can therefore impersonate only `https://192.168.0.1` and `u60.home.arpa` (for example another network's router that also sits at 192.168.0.1), not every private address and `home.arpa` name. Tested: a certificate for `nas.home.arpa` + `192.168.5.5`, `192.168.0.2` or `10.20.30.40` signed with the stored issuing key is refused by webpki (`tls::tests`), OpenSSL 4.0.3 and macOS trust evaluation (2026-10-24). The cost: after a LAN address change the certificate names only `u60.home.arpa` (the hosts line follows the new address, so the name keeps working) and Settings says "Reset HTTPS and turn it on again" to cover the new address (each device then trusts the new CA). A LAN address outside 10/8, 172.16/12, 192.168/16 at Turn On gives a CA for the name only (every IPv4 address excluded). A `ZTE_AGENT_TLS_NAME` changed after Turn On is not covered either; Settings says so.
- **Why two CAs.** The test that settled it (2026-10-24, Android 16 emulator, Chrome 133, the root installed as a user CA through Settings): with a single name-constrained root, a certificate for `10.0.2.2` *and* `example.com` loaded without a warning, as did one for `127.0.0.1`: Android's system verifier (which Chrome for Android uses) ignores a user-installed trust anchor's name constraints. With the constrained issuing CA in the chain, both were refused ("Your connection is not private", scrambled credentials) and the in-range certificate loaded. Every verifier enforces an intermediate's constraints (RFC 5280); the root's are kept for those that also honour an anchor's (Apple, OpenSSL and webpki do, tested). The only key on the router (`issuing.key`) can vouch for nothing outside the constraints. They, not `pathLen`, are what holds: a CA that key makes for itself (self-issued, which RFC 5280 does not count against `pathLen`; macOS accepted one in the security review) still inherits the constraints, so its certificate for `example.com` is refused. IPv6 is excluded so that a verifier treating it as a name type of its own cannot be used. serverAuth on both CAs keeps them from code signing and e-mail where EKUs chain (Windows, NSS, Chrome).
- **397 days:** Apple and Chrome limit publicly trusted TLS certificates to 398 days; Apple limits every TLS certificate, user-trusted roots included, to 825 days and requires serverAuth and a SAN. The CA's 10 years are not limited for user-installed roots; when it ends, Reset.
- **Clock.** After a fast-boot power-on the router's clock is stale until NITZ/NTP sets it, and the firmware's NITZ can be +8 h off. So: dates are backdated 2 days; `Tls::utc` is *verified* (the live activity's TLS-checked UTC, `LiveActivity::verified_utc`), *unverified* (the router's clock, not before 2026-10-01 nor before the CA's own date) or *unset*. Turning on and Renew are owner actions whose question shows the date (and says when it was not checked); they refuse an unset clock. Automatic renewal (fewer than 30 days left) needs the verified clock, and the router's own clock is never used without the owner (not at start either). **The verified clock exists only while a Live Activity APNs provider is configured** (`ZTE_AGENT_LIVE_ACTIVITY_CONFIG`, which needs an Apple developer key; README): without one the certificate is never renewed by itself, and about every 13 months Settings shows "Certificate expires" and "Renew Certificate" for the last 30 days (`renew_due` in `GET /api/https`); after the end, devices get a certificate error until Settings › Renew Certificate over `http://192.168.0.1:9090/ui/settings`. (Renewing unattended on the unverified clock within a sanity window is an open owner decision.)
- **Issued again, no timers:** at agent start (thread `tls-start`, once), at a TLS connection (`Tls::wants_check`, memory only on the runtime thread: the connection reached a private address that is neither the certificate's nor the LAN address last read, or fewer than 30 days are left by the router's clock; then `check` on the blocking pool, awaited for at most 2 s before the handshake, at most once a minute) and after a LAN apply (`router_lan_set`, the posted `lan_ipaddr`, for the apps too). When the address the certificate should name changes (the CA covers the new one, or not: then the name alone) it is issued again with the old dates (no clock needed); the hosts line follows the LAN address either way, and Settings' certificate line is worked out again each time (cleared once nothing is wrong). The new key is swapped in for the next handshake (`tls::Keys`, read by the rustls resolver at every handshake); open connections keep theirs.
- **Files** in `/data/zte-agent-tls/`: the directory 0700 and keys 0600 (both set again at start when found readable by others), each file written beside its name, synced and renamed, then the directory synced. A server pair that is missing or damaged at start (a power cut between saving the new key and its certificate, a full disk) is issued again from the same CA, dated as the old certificate when that still reads (no clock needed), else by the verified clock; with neither, the CA is kept and Settings says "Turn On HTTPS issues a new one from the same certificate authority" (devices keep trusting it). Files that cannot be used at all leave HTTPS off with "Turn On HTTPS makes a new certificate authority…; Reset HTTPS deletes these files." (Reset is offered while off then). Keys are never logged, rendered or served (tests check the API answer, the profile and the install page for them).

**The listener** (`httpd::tls::supervise`, on the same current-thread runtime as :9090): it waits on `Tls::subscribe` (a `watch` channel, no polling), binds `0.0.0.0:9443` (`ZTE_AGENT_TLS_BIND`) when HTTPS is on and stops when it is reset: the port closes and every connection it served ends (a `watch` sender dropped; a request in progress, such as the Reset's own reply, may finish within 2 s; keep-alive connections and live streams end then). rustls 0.23 with the ring provider, TLS 1.3 and 1.2, ALPN `http/1.1`, 64 resumable sessions, a new `ServerConfig` each time it starts (a reset also drops every resumable session, so a client cannot resume one made under the old CA), 10 s for a handshake. The chain is the server certificate and the issuing CA's. Same router, same mobile-side check (`mobile::Guard::twin`, its own table and its own fail-open flag, so the firewall questions' "this web UI may become reachable" follows either listener), the same connection caps as :9090 and shared with it (`Caps`: 64 in all, 16 per LAN address, the last 8 for loopback). A bind that fails, or a listener that ends by itself, is shown in Settings ("On · not listening", the error and **Try Again**, which is Turn On) and tried again only then: never in a loop. Requests carry the `Secure` extension; the cookie and origin translations are under [Sessions and CSRF](#sessions-and-csrf). Handshakes run on the runtime thread (about 1 ms of CPU each on the router's Cortex-A55, estimated from 94 µs on an M4 Max); a LAN host opening them in a loop is bounded by the connection caps and slows :9090 by milliseconds, not more (no rate limit: a slow-handshake semaphore would let one stalled client block the others).

**The local name** (`tls::hosts`): `/tmp/hosts/zte-agent` holds `<LAN address> u60.home.arpa` (dnsmasq's `lan_dns` instance reads the `addn-hosts` directory `/tmp/hosts` again on SIGHUP; `/tmp` is tmpfs, so the agent writes the line again at every start). Only a change is written and only a change signals. The file is first written as `/tmp/.zte-agent-hosts.tmp` (beside the directory, never inside it: dnsmasq reads every file there), created new (`O_EXCL`, mode 0644: a link someone planted at that name in the world-writable `/tmp` is removed, never followed), then renamed into place. SIGHUP goes to the pid in `/var/run/dnsmasq/dnsmasq.lan_dns.pid` if its `/proc/<pid>/comm` is `dnsmasq`, else to every `dnsmasq` in `/proc`, never to anything else (on SIGHUP dnsmasq also re-runs a configured `dhcp-script` for every lease: a device check). Reset removes the line (and signals). `ZTE_AGENT_TLS_NAME` sets another name under `.home.arpa` (anything else is ignored and logged). The name is a Host only over HTTPS ([Request pipeline](#request-pipeline)). Devices with their own DNS (Android's Private DNS set to a provider, DNS over HTTPS in the browser, a VPN) may not see the name; the address URL always works while the CA covers it.

**Settings › HTTPS & Install as App** (`pages::https`): off: "HTTPS Off" and "Turn On HTTPS" (and, when files were left that could not be used or a CA was kept, the reason and "Reset HTTPS"); on: "HTTPS On" (or "On · not listening" with **Try Again**), "Certificate valid until <date>" ("Certificate expires" and "Renew Certificate" within 30 days by the router's clock), the https addresses as links, "Install on Your Devices", "Reset HTTPS" (red), and a footer: over HTTPS "You are using HTTPS…", over plain http (not over Tailscale, whose names the certificate does not hold) "This page is plain http. Once this device trusts the router's certificate authority (Install on Your Devices), open https://<address>:9443/ui/ …"; the login page over plain http says the same. Turn On's question: what is created, that each device trusts the authority once and that it can vouch only for this router's LAN address and the name (and that after a LAN address change only the name works until Reset), the router's clock (checked over the internet or not), that :9090 stays; with a kept CA, that it issues a new certificate from it. Reset's: what is deleted, that devices must remove the old authority and trust a new one, and over HTTPS that this page stops working. Install on Your Devices: the root's name, what it can vouch for, its SHA-256 fingerprint (line breaks only between byte pairs; screen readers get it once, whole) and Windows' SHA-1 "Thumbprint", where each device shows the fingerprint (iPhone: Profile Downloaded › More Details before Install; Mac: Keychain Access; Android: Trusted credentials › User; Windows: Details) and that case and separators do not matter; over plain http, that the page and the download could be changed together by someone on the network and how to check against a source they cannot fake (this page over HTTPS on a device that already trusts the CA, or `sha256sum /data/zte-agent-tls/ca.crt` over SSH); the two downloads, the steps for iPhone and iPad, Android, Mac, Windows (Firefox 120+ on Windows, macOS and Android uses the system's roots; on Linux the manual import), then how to install the app (Chrome: Install; Safari on iPhone: ••• › Share › View More › Add to Home Screen; Safari on Mac: Add to Dock) and the DNS note. The profile: one `com.apple.security.root` payload, unsigned ("Not Signed" on iOS), its description saying what the CA can vouch for, ids from the CA's digest (the same CA gives the same profile).

**`GET /api/https`** (bearer token when a password is set; general lane; read-only): off `{"ok":true,"data":{"enabled":false,"port":9443,"name":"u60.home.arpa","error":null}}`; on `{"ok":true,"data":{"enabled":true,"listening":true,"port":9443,"ip":"192.168.0.1","name":"u60.home.arpa","urls":["https://192.168.0.1:9443/ui/","https://u60.home.arpa:9443/ui/"],"not_after":<unix s>,"renew_due":false,"ca_name":"U60 Pro local CA 1A2B3C4D","ca_sha256":"AB:CD:…","ca_covers":["192.168.0.1","u60.home.arpa"],"ca_crt":"/ui/https/u60-pro-ca.crt","ca_mobileconfig":"/ui/https/u60-pro-ca.mobileconfig","error":null}}`. Turning on and resetting are web UI actions only.

## Privacy

- Never rendered: IMEI (Device Info shows its last 4 digits, "…0042"; the read keeps only those, so the whole number never reaches a renderer; owner decision, the app shows it whole), IMSI and MSISDN (the router's own number) except on SIM Card as below, full ICCIDs, full MAC addresses (the `clients` topic reads MACs; only the renderers mask them). The dashboard shows only how many devices are connected. Device Info does not read the SIM (the app reads it and shows none of it).
- SIM Card (owner decision; the app shows them whole): the ICCID and MSISDN as their last 4 digits ("…4242"), the IMSI as its network and last 4 digits ("001/01 …4242": the card's MCC and MNC when they lead it, which the page shows on its own row anyway, else the first 3 and 2 digits). The `sim` topic carries the whole values; only these renderers see them, also in the stream frames. PINs, PUKs and unlock codes are only in POST bodies: never in a URL, a page, a log or the token store (its digest is keyed); a sheet shown again has empty fields. The agent passes them to `ubus` on its command line (visible in `/proc` for the call's duration), and the firmware's `zte_topsw_mdm` has format strings that print a PIN, PUK and NCK to its log (`mdm.str`; not checked on the device): both outside the web UI.
- Add eSIM: activation and confirmation codes are only in the post's body (multipart) and the agent's request: never drawn into a page (the fields are always empty), put in a URL, a fragment, a result line or a log, and never kept (no draft; the token store keeps an HMAC of them with the process's key). Uploaded photos are held in RAM only while read and decoded, then dropped; never stored or logged (the decoding process gets them over a pipe, its stderr is discarded and it writes only its answer). An operator's error is shown without any word shaped like an activation code.
- eSIM Profiles: ICCIDs as their last 4 digits ("…1234"); profiles are named in URLs and forms by an opaque key (an HMAC of the ICCID with a per-process key, 16 hex; the full ICCID only goes to the agent's handlers in-process); the EID masked ("•••• •••• •••• …1234") unless the page was asked for it (`?eid=1`, an explicit GET; never in a fragment, a stream frame, a URL or a log). Profile names, providers and nicknames are shown as the app does. The names of the last list read are kept in RAM (by ICCID) so a switch's live card can name its target.
- SIM Services: USSD answers and toolkit texts can hold balances, numbers or voucher codes: shown as they are (the plan's "none": the app shows them, and a masked voucher could not be used), on signed-in `no-store` pages only, kept in RAM for the session that asked (10 minutes, dropped on logout), never in a URL (`?u=` is the post's used token), a log or `<title>`. A text typed for the SIM is only posted (a hidden one in a password field). A USSD code that carries a SIM PIN or PUK is refused and never shown again.
- Connected Devices shows what Wi-Fi & devices shows (the same rows' data and masking: name, IPv4, the MAC's last 2 octets, no IPv6). Its search is posted to the page, as Messages' (so its text, which may be a device name, is in no URL, the history or `next`; a `q` in the URL is ignored), and matches only what is shown: the masked name and MAC and the IPv4 address (a search for hidden octets finds nothing). A failed read is the first row ("Couldn't update: …"), as the app's red row; the network icon is secondary grey.
- Wi-Fi & devices lists each device's name (DHCP host name, else the host-hint name) and IPv4 address, with the MAC masked to its last 2 octets (`••:••:••:••:3a:7f`; the app shows it whole) and no IPv6 address (owner decision). A name that spells 3 or more octets of the device's MAC (6+ hex digits, or octets joined by `:` or `-`, as in `shellyplus1pm-02032ab12345`) has those characters masked too. The list is live, so these also travel in its stream frames; never in URLs or fragment ids.
- Wi-Fi passwords appear only on Share Wi-Fi: as text only after "Show password" (`?show=1`), and in the join QR code, which the page always shows (as the app's card). The page is never live, `no-store` like every page, and the password is never in a URL, a log or another page; the shown password is marked `translate="no"`. The Wi-Fi card's read drops the keys before rendering. Known limit: `no-store` does not reliably keep a page out of a browser's back-forward cache (WebKit may keep it), so on a shared device Back after logging out can show a Share Wi-Fi page from memory; close the tab. (`Clear-Site-Data` would not help: browsers honour it only in secure contexts, and the agent speaks plain HTTP.)
- Processes shows process names and PIDs (as the app).
- SMS pages show the numbers you exchange messages with and the message text, unmasked as in the app (owner decision), on signed-in SMS pages only: never in `<title>` (a conversation's is "Conversation"; the number is its heading), a URL or query string (conversations by opaque key; the search is a POST to Messages, so its text is in the page only: the storage items then post the search form to the other store's page, and links, the stream and `next` carry no search; a `q` typed into the URL is ignored, and the login drops it), a live fragment id or stream frame, or a log. Rendered times use the router's own time zone everywhere, at each message's date (so a winter message keeps its winter time in summer; list labels count from the router clock, in the app's abbreviated words: "5 min. ago", "1 mo. ago", "in 2 min." for a time ahead of it; the date while the router clock is unset).
- Forwarding secrets (bot tokens, webhook, Discord and Slack URLs, header values, ntfy tokens) are never rendered: the config read drops them before any renderer, a webhook shows as its host, and the rule form's secret fields are never filled; secrets typed into a form that is shown again are kept in RAM by its token, never in the page, and a refused field that may hold one (an ntfy URL's password or query, a pasted "Name: value" header line) is not echoed. An empty secret field keeps the saved secret only for the same destination type and server (the merge rules under New Rule / Edit Rule), for Save and Test alike. Chat IDs, ntfy topics and forward numbers are shown, as the app's. Forwarder errors (Test, Save, the log, Retry) lose the URI the HTTP client quotes in two of its messages ("bad uri: <uri> …", "configured for https only: <uri>"), which could hold a webhook path or a bot token (`web::forward::redact`).
- Forward Log shows each forward's sender and the message's first 80 bytes (often a one-time code), as the app, on signed-in pages only (in either tab); never the message's full text or its date, and nothing of it in a URL (the Retry form posts ids and a time).
- WAN addresses, PCI and cell ID appear only on signed-in pages; so do Cell Lock's PCIs and EARFCNs and Mobile Network's operator names and PLMNs (the registration question's URL carries the PLMN, the RAT and the network's name, no personal data).
- The router password of "Reboot Now", Reboot Router and Factory Reset is posted only, compared on the router in constant time (counted by the login rate limit, the same buckets as a login), and never echoed, logged or kept.
- The preference cookies (theme, refresh interval) hold fixed values only; nothing about the session, the router or what was typed.
- WiFi, guest WiFi and APN passwords are never drawn into a page, a URL, a fragment or a log (owner decision; the app fills them): the reads drop them before any renderer, the fields are always empty ("Leave empty to keep"), and one typed into a form waits in the session's draft (RAM, an hour after the last try, dropped on logout and once sent; a send that failed keeps it for the retry), never in the page: the question's form carries only the token and the draft's random revision. The digest a token keeps covers the revision only.
- Firewall: the MAC/IP/Port filters' MAC addresses show only their last 2 octets (`••:••:••:••:3a:7f`; the app shows them whole); LAN addresses and ports are shown as the app's.
- DNS Cache shows the domains the router's devices looked up (the network's browsing history), on signed-in `no-store` pages only; its search is posted, never in a URL or `next`.
- AT Terminal: the answers are raw modem output, so every run of 14 or more digits (an IMEI, IMSI or ICCID; owner decision: 14–20) shows only its last 4 (`•••••••••••0042`), in the stored history too (the whole number is never kept; masked before the 4 KiB cut, so a cut never leaves part of one in clear); the "IMEI" quick command is left out. SIM PINs and PUKs are never kept: from `+CPIN=`, `+CPIN2=`, `+CLCK=` or `+CPWD=` on, every run of 4 or more digits is "••••" in the stored command and answer (the modem's echo). Shorter numbers (a phone number in `AT+CLCC` or `AT+CNUM`) are shown as the modem gives them. The history is per session, in RAM, and goes on logout; commands are never in a URL (only the fixed quick commands are). The "Dangerous Command" question names the command masked the same way (its hidden field keeps it as typed, for Send Anyway and Cancel).
- Device error text is escaped and cut to 120 characters. The `?saved=` notice comes from a fixed table; a `?r=<id>` result is looked up for the session, never read from the URL.
- The QR code's security type follows the app's, except that a network without an `encryption` option (which the card calls "Open") is encoded as open (`T:nopass`), not WPA.
- The web code logs nothing.

## Assets

- `build.rs` checks the SHA-256 of `src/web/assets/datastar-1.0.4.js` (`727844ad…cf91`), so it must stay byte-identical (`.gitattributes` keeps line endings as they are). It also draws the icons (SVG, and PNG 180/192/512; no image files are committed), makes the two theme stylesheets from `app.css` (`theme-light.css`: the light values of the properties the `prefers-color-scheme: dark` block sets, `theme-dark.css`: that block's, each with its `color-scheme`; about 430 bytes each, so a colour changed in `app.css` changes them too), gzips the text assets and writes the manifest.
- File names carry a content hash. Assets are served with `Cache-Control: public, max-age=31536000, immutable` and a strong ETag; text assets are stored gzipped, with an identity fallback. The manifest is `no-cache` with an ETag.

## Testing

- `cargo test -p zte-agent` (or `web::`, `httpd::`, `events::`, `auth::`). The tests run on the build machine with fake clocks, a fake RNG and fake readers, through the whole router (`tower::ServiceExt::oneshot`) and a real accept loop on 127.0.0.1. `web::pages::fake` makes page loads of one test's `AppState` read a given value (every topic, the Wi-Fi and guest status), so hostile data goes through the real routes; `web::sms::fake` is the SMS device, and `web::pages::device` stands in for the device behind a change (Speed Test's start, Enable ADB, Band Lock, an AT command, the Router changes: each call recorded, a reply by path or by "<path>#<n>" for the n-th call, optionally slow; its `gets` answer page-load reads of API routes, `pages::api_get`; the speed test's own run is tested against an unreachable local server and a slow local one, and the agent never fetches the server list in tests), `web::forward::fake` answers forwarding test sends and retries, and the log when a test sets one (the agent's log cannot be filled from outside; the forwarding config and rules are each test `AppState`'s own, in memory; their handlers try to save to `/data/local/tmp`, which a build machine does not have, and the tests check that).
- `cargo clippy -p zte-agent --all-targets`, then the release cross build and its size.
